# Parallel builder fleets — N concurrent Claude Code sessions on one repository

> reviewed: 2026-07-17 · tiers: the closed vocabulary in README rule 2 (the audit prints it on error)

Running N autonomous builder sessions against one repo forces four questions — isolation, merge topology, work allocation, fleet sizing — and the field has hard numbers for each. This note is the evidence base behind **D-330** (multi-writer merge topology, ratified 2026-07-17: scaled self-merge + strict landing rule; resolver runbook trigger-gated, not built) and grounds the fleet program under epic **#93**: **#331** (concurrent-writers v3), **#332** (fleet_size), **#333** (review tripwires). Surveyed under **#328**; the five raw lens sweeps (every source, tier call, and unverified flag) are that ticket's provenance record.

## State of the art

### Isolation

- The industry converged on one-worktree-one-branch-one-session: claude-squad, Conductor, Crystal, vibe-kanban, uzi, Superset, and Claude Code natively all isolate parallel agents this way; Claude Code ships the mechanics (`claude --worktree`, `.worktreeinclude` env copying, `git worktree lock` while an agent runs) [production-proven] (source: https://code.claude.com/docs/en/worktrees, accessed 2026-07-17; representative third-party: https://github.com/smtg-ai/claude-squad, accessed 2026-07-17)
- The shared-checkout alternative fails by design — Copilot CLI /fleet sub-agents "share a filesystem with no file locking. If two agents write to the same file, the last one to finish wins — silently" [production-proven] (source: https://github.blog/ai-and-ml/github-copilot/run-multiple-agents-at-once-with-fleet-in-copilot-cli/, accessed 2026-07-17)

### Merge topology

- The discipline every merge queue encodes is the Not-Rocket-Science Rule: test the merged state of change + current main *before* landing, because two individually-green PRs can combine into a red main with no textual conflict at all [production-proven] (source: https://graydon2.dreamwidth.org/1597.html, accessed 2026-07-17; https://bors.tech/, accessed 2026-07-17)
- GitHub's merge queue is available only to public org-owned repos or private repos on Enterprise Cloud; a private free-plan repo gets neither the queue nor branch protection ("You can enable branch restrictions in public repositories owned by a GitHub Free organization and in all repositories owned by an organization using GitHub Team or GitHub Enterprise Cloud") [production-proven] (source: https://github.com/orgs/community/discussions/51483, accessed 2026-07-17; https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches, accessed 2026-07-17)
- bors-ng is the reference resolver algorithm: batch approved PRs onto an ephemeral staging branch rebuilt from main per cycle, run CI once on the tip, bisect the batch on failure — O(E·log N) builds for E failures; its known poisons are resolver-as-SPOF, flaky tests, and slow suites [production-proven] (source: https://github.com/bors-ng/bors-ng, accessed 2026-07-17; failure modes: https://www.aviator.co/blog/what-is-bors/, accessed 2026-07-17)
- Persistent integration branches are the documented failure mode: the git-flow retrospective record shows durable develop-style branches defer integration and breed repeated team errors [experimental] (source: https://www.endoflineblog.com/gitflow-considered-harmful, accessed 2026-07-17); trunk-based development states the positive form at "35,000 developers" scale in Google's monorepo [production-proven] (source: https://trunkbaseddevelopment.com/, accessed 2026-07-17)
- The agent-fleet version — Yegge's "Merge Queue problem": workers branched from identical baselines compound conflicts as merges land ("When the fourth agent D finishes its work, a rebase may no longer be feasible"), and repo-wide restructurings forcibly serialize every stream [experimental] (source: https://steve-yegge.medium.com/six-new-tips-for-better-coding-with-agents-d4e9c86e42a9, accessed 2026-07-17)
- The self-merge landing rule has a named precedent: Kodiak's loop — auto-update branch with base, wait for green, merge, next — is a merge queue built from branch-protection semantics alone, one full CI run per landing [production-proven] (source: https://kodiakhq.com/, accessed 2026-07-17)

### Coordination & work allocation

- Collision prevention is allocation-time work, not runtime locking: Anthropic's orchestrator prevents duplicated effort purely through "clear task boundaries" per subagent — vague task specs produced redundant overlapping work [production-proven] (source: https://www.anthropic.com/engineering/multi-agent-research-system, accessed 2026-07-17)
- Claude Code agent teams (experimental flag) run a shared task list where "Task claiming uses file locking to prevent race conditions"; the file-conflict rule is "Break the work so each teammate owns a different set of files"; sizing guidance: "Start with 3-5 teammates" with "5-6 tasks per teammate" [production-proven] (source: https://code.claude.com/docs/en/agent-teams, accessed 2026-07-17)
- Disjoint-file-set scheduling is a solved research problem: Cassandra models each task by its file-edit set and orders tasks to minimize concurrent overlap; its study also shows most integration pain is semantic, not textual — of *clean* merges, 2.1–14.7% still broke the build and 5.6–35% broke tests [published] (source: https://epiclab.github.io/publications/icse13-kasi.pdf, accessed 2026-07-17)
- Prediction is asymmetric: classifiers certify *safe* (non-conflicting) merges at F1 0.95–0.97 but predict conflicts at only F1 0.57–0.68 — certify parallel-safe pairs, don't rank risk [published] (source: https://arxiv.org/abs/1907.06274, accessed 2026-07-17); and across 21,488 merge scenarios, none of 7 developer-suggested indicators (commit counts, developer counts, duration, change size) predicted conflict frequency [published] (source: https://link.springer.com/article/10.1007/s10515-017-0227-0, accessed 2026-07-17)
- File overlap between open PRs is the signal that does work: Microsoft's ConE (deployed on 234 repos, 26k PRs evaluated, >70% of notifications rated useful) — and concurrently-edited files are more likely to introduce bugs, i.e. overlap predicts logical conflicts too [published] (source: https://arxiv.org/abs/2101.06542, accessed 2026-07-17). Applied here: a merge-time checkpoint editing the same Status/ROADMAP lines on every PR makes every pair of in-flight branches conflict by construction — the hot-file hazard is self-inflicted, and the fix is keeping hot shared files out of parallel feature branches entirely.
- Lease semantics, canonically: SQS visibility timeout — a claim hides the work item, a heartbeat extends it, a dead consumer's item reappears for another consumer, repeated failure routes to a dead-letter queue [production-proven] (source: https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html, accessed 2026-07-17); the same shape (claim = scope declaration + timestamp, stale claims reaped after 2 hours) appears in a 20–50-session Claude Code farm's lock registry [experimental] (source: https://github.com/Dicklesworthstone/claude_code_agent_farm, accessed 2026-07-17)

### Fleet sizing & field reports

- The sustainable band clusters at 3–5 concurrent sessions: "The honest ceiling: 3-5 parallel sessions for most users, not 10" [experimental] (source: https://findskill.ai/blog/claude-code-10-parallel-agents-week-1/, accessed 2026-07-17); mature orchestrator users "regularly run 3-5 instances" [experimental] (source: https://www.aviator.co/blog/the-rise-of-coding-agent-orchestrators/, accessed 2026-07-17); a production practitioner sustains exactly 5 worktree sessions as engineering-manager work [experimental] (source: https://every.to/source-code/how-i-use-claude-code-to-ship-like-a-team-of-five-6f23f136-52ab-455f-a997-101c071613aa, accessed 2026-07-17)
- The ceiling is human review, not the agents: the Terragon founder ran ~30 tasks/day across "10+ concurrent work streams" and spent the rest of the day "clearing these tasks and reviewing the agent's work" [experimental] (source: https://ymichael.com/2025/07/15/claude-code-unleashed.html, accessed 2026-07-17)
- At 16 concurrent pending changes Uber measured ~40% conflict probability, with mainline green only 52% of the time pre-SubmitQueue; its fix gates on build-target disjointness first, speculation second [published] (source: https://blog.acolyer.org/2019/04/18/keeping-master-green-at-scale/, accessed 2026-07-17)
- Agent PRs conflict at 27.67% overall (142k+ agent PRs, 59k+ repos), strongly size-dependent: small ~10%, medium ~30–33% — slice size is the biggest controllable conflict lever [published] (source: https://arxiv.org/html/2604.03551v2, accessed 2026-07-17)
- Above the band, precedents add a dedicated integrator: MultiDevin's manager "resolves any conflicts" for workers run "10 at a time" [production-proven] (source: https://cognition.com/blog/devin-can-now-manage-devins, accessed 2026-07-17); Imbue's 100+-agent run used an integrator that merges uncontroversial commits first, then ranks and sequentially resolves the rest [experimental] (source: https://imbue.com/product/mngr_part_2/, accessed 2026-07-17); Gas Town's Refinery is a Bors-style bisecting queue over a git-backed tracker (Beads), claiming 20–30 agent scale — but a week-long field trial ended in abandonment: orphaned processes, token burn, constant manual prodding [experimental] (source: https://github.com/gastownhall/gastown, accessed 2026-07-17; https://tenzinwangdhen.com/posts/gastown-good-bad-ugly/, accessed 2026-07-17)
- Token economics: teammate-style parallel sessions cost linearly ("Token costs scale linearly"; each teammate a separate instance) [production-proven] (source: https://code.claude.com/docs/en/agent-teams, accessed 2026-07-17); each agent run spends ~20–50k tokens on context bootstrap alone [experimental] (source: https://hn.algolia.com/api/v1/items/47629485, accessed 2026-07-17); orchestrated multi-agent systems run ~15× chat-token cost vs ~4× for single agents — the premium is the relay, not the workers [production-proven] (source: https://www.anthropic.com/engineering/multi-agent-research-system, accessed 2026-07-17)

### Where the bottleneck moves

- Merge-point queueing is a utilization problem: queue length grows as ~ρ²/(1−ρ) [published] (source: https://teropa.info/blog/2016/04/02/a-dash-of-queueing-theory.html, accessed 2026-07-17); the machinery threshold is Uber-scale — ~1,000 changes/day at 30-min CI makes naive serialization a ~20-day queue [published] (source: https://blog.acolyer.org/2019/04/18/keeping-master-green-at-scale/, accessed 2026-07-17). A handful of sessions against minutes-long CI sits at single-digit-percent utilization; batching there is counterproductive — a worked example shows a 10× batch producing 25× cycle time [published] (source: https://less.works/less/principles/queueing_theory, accessed 2026-07-17)
- When authoring parallelizes, review is the constraint that binds: high-AI-adoption teams shipped +98% PRs but review time rose +91% [production-proven] (source: https://www.faros.ai/blog/ai-software-engineering, accessed 2026-07-17), climbing to +441% median time-in-review with 31% more PRs merging with *no review at all* — saturation fails silently as gate erosion, not visibly as queue growth [production-proven] (source: https://www.faros.ai/blog/key-takeaways-from-the-dora-report-2025, accessed 2026-07-17)
- Agentic-AI PRs wait 5.3× longer for first review pickup than unassisted PRs [experimental] (source: https://blog.codacy.com/ai-breaking-code-review-how-engineering-teams-survive-pr-bottleneck, accessed 2026-07-17 — secondary aggregation of LinearB data); reviewer bug-detection effectiveness collapses with diff size, 87% at ≤100 lines to 28% at 1,000+ [experimental] (source: https://gitautoreview.com/blog/hidden-cost-of-slow-code-reviews, accessed 2026-07-17)
- Zuul's queue governor is directly portable to session count: the speculation window grows +1 per successful merge and halves on failure, default 20 — TCP-style congestion control on concurrency [production-proven] (source: https://zuul-ci.org/docs/zuul/latest/gating.html, accessed 2026-07-17)

## Validations (what the field confirms about this repo's shape)

- **One-writer-per-checkout is the industry answer, generalized.** The worktree-per-session convergence *is* our rule at N: N builders = N worktrees (or N clones on N machines — same topology), with the isolation mechanics already native to Claude Code [production-proven] (source: https://code.claude.com/docs/en/worktrees, accessed 2026-07-17)
- **Tracker-as-only-coordination-bus is validated by its closest analog, not by peers.** Nobody surveyed coordinates through GitHub issues; but Gas Town runs its entire fleet — work items, merge requests, agent notes — on a git-backed issue tracker at 5× our target scale, validating the shape on the bus we already have [experimental] (source: https://github.com/gastownhall/gastown, accessed 2026-07-17)
- **Claim-by-branch-push is the field's atomic claim primitive, free.** Agent teams needed file locking to make task claiming race-safe [production-proven] (source: https://code.claude.com/docs/en/agent-teams, accessed 2026-07-17); remote git ref creation is atomic per-ref, so racing sessions cannot both create `slice-<NN>` — the push is the test-and-set, the claim comment the human-visible record — derived from the atomicity of git's own ref-update semantics, not from a fetched field report [analysis]
- **The small-slices policy doubles as the concurrency-safety policy.** Agent-PR conflict rates roughly triple from small to medium PRs [published] (source: https://arxiv.org/html/2604.03551v2, accessed 2026-07-17), and Google's under-4-hour review median rests on a 24-line median change [published] (source: https://sback.it/publications/icse2018seip.pdf, accessed 2026-07-17)
- **EXP-01's measured ~2–4× relay tax is the same economics as the ~15× orchestrator multiplier** [production-proven] (source: https://www.anthropic.com/engineering/multi-agent-research-system, accessed 2026-07-17) — tracker-coordinated independent sessions pay linear cost plus bootstrap and zero relay; issues-as-bus is already the token-efficient topology.

## Rejections (recorded so future sessions don't re-litigate)

- **Persistent integration branch** — durably divergent branches defer integration and compound baseline drift; an *ephemeral* per-batch staging branch is just a merge-queue implementation detail (source: https://www.endoflineblog.com/gitflow-considered-harmful, accessed 2026-07-17)
- **Day-one resolver at N=4** — the integrator precedent lives at 10–100+ agents, and the resolver is itself a serial bottleneck and SPOF; D-330 shelves it as a trigger-gated runbook instead (source: https://www.aviator.co/blog/what-is-bors/, accessed 2026-07-17)
- **Platform merge queue** — unavailable to this repo class (org+public or Enterprise Cloud only) (source: https://github.com/orgs/community/discussions/51483, accessed 2026-07-17)
- **Speculative/batched CI at our volume** — pays at hundreds-to-thousands of changes/day; at low volume batch math works against you (source: https://less.works/less/principles/queueing_theory, accessed 2026-07-17)
- **Conflict-risk prediction as a scheduler input** — conflict-class F1 0.57–0.68 is too weak to gate on; certify-safe via path disjointness (the F1 0.95+ direction) instead (source: https://arxiv.org/abs/1907.06274, accessed 2026-07-17)
- **Shared checkout for any two sessions** — documented silent last-writer-wins (source: https://github.blog/ai-and-ml/github-copilot/run-multiple-agents-at-once-with-fleet-in-copilot-cli/, accessed 2026-07-17)
- **Runtime file locking / in-repo lock registries** — works at 20–50 sessions but violates the issues-only bus and adds merge noise; its value (scope declaration + stale reaping) ports to issue comments losslessly, and disjointness is decided at allocation time anyway (source: https://github.com/Dicklesworthstone/claude_code_agent_farm, accessed 2026-07-17)

## Feasibility path

D-330's ratified topology — scaled self-merge with a strict landing rule (rebase onto current main, re-run CI, merge only if still green and main unmoved; the Kodiak loop run by the merging session) — is exactly what the evidence supports at this scale. The program maps as:

- **#331 (concurrent-writers v3):** claim-by-branch-push as the arbiter; lease semantics on the claim (timestamped comment, branch pushes as heartbeat, reclaim rule after quiet hours, dead-letter `needs-human` label after two burned leases); an `exclusive` label for repo-wide-restructuring tickets that pause all other builders; plus the merge-owned hot-file change — Status/ROADMAP checkpoint stamps written only by the merging session against fresh main, never carried on feature branches.
- **#332 (fleet_size):** N = min(size of the largest pairwise file-disjoint set of ready tickets, the vendor band above with its ready-tickets-per-builder floor, a WIP cap on open PRs awaiting review), adjusted by a Zuul-style governor (+1 on clean-landing streaks, halve on a red-main or landing collision).
- **#333 (review tripwires):** instrument review pickup latency, unreviewed-merge fraction (target zero), and rebase-conflict rate at merge — the last is the documented trigger that un-shelves the resolver runbook.

## Candidate experiments

- **EXP-02 (amended):** two concurrent builders in worktrees of one checkout on one machine — no second machine needed — running the v3 claim protocol on disjoint tickets; metrics: duplicate claims, landing collisions, protocol token overhead; baseline: one solo session over the same ticket set.
- **4-wide field trial** on a downstream repo with a large independent-ticket backlog; metrics: rebase-conflict rate at merge, duplicate claims, review pickup latency, unreviewed merges, tokens per merged PR — against the same repo's solo baseline.
