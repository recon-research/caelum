# Adversarial Review (Parallel, Multi-Lens)

Run several **independent reviewers in parallel**, each with a different lens and a mandate to *break* the change, then reconcile and fix. A reviewer told to confirm tends to confirm; reviewers told to falsify, from distinct angles, surface the real defects a single pass misses. This is the gate before a feature merges. Read paths / commands / stack / invariants from `PROJECT_CONVENTIONS.md` and `docs/ARCHITECTURE.md`.

## The design: parallel review is read-only; fixing is coordinated

The one rule that makes the parallel fan-out safe — **so the reviewers never trample each other's work**:

- **Review phase = strictly read-only.** Every reviewer *analyzes* the diff and *returns findings*. **No reviewer edits the working tree.** That is precisely *why* they can run concurrently without trampling — there is nothing to trample, because nobody writes. A reviewer that wants to "just fix it inline" is a setup bug; stop it.
- **Execution is deferred to an isolated verify stage.** "Read-only" covers edits, not builds: parallel agents *running* builds/tests on one shared checkout collide — contended build dirs, racing compiles — **manufacturing phantom failures that look exactly like real flakiness** (this once produced a spurious Critical finding on a real project). So no lens executes: a runtime claim routes post-fan-out to step 4's [`repro-verifier`](../../agents/repro-verifier.md) in its own worktree; pure Grep/Read reviewers share the tree.
- **Fix phase = a single coordinated writer.** Apply the must-fix set *after* the fan-out, from one place. By default **serially** in the working tree (one writer, no conflicts). Parallelize fixes only when they touch **disjoint files**, and then **isolate each in its own git worktree/branch** (a worktree or branch per fix) and merge back — never two fix agents writing the same tree at once.

Keep the stages strictly separated: reviewers find; the verifier executes; one coordinated pass fixes. (This shape is also the token-efficient one: each reviewer burns its own subagent context; the orchestrator holds only the findings tables.)

## When to run

A checkpoint gate for **high-stakes or novel** work at the **end of a feature, before merge** (or before closing a multi-PR epic) — not every change. Reach for it on: nontrivial logic or math, concurrency / shared state, security- or safety-sensitive code, a new subsystem, a spec↔impl or producer↔consumer mirror, or a large refactor. Skip trivial / mechanical changes (use `/code-review` or `definition_of_done`); over-use trains noise.

## Procedure

1. **Frame the target + the claims to falsify.** Pin down exactly what changed (the diff, the files) and the **load-bearing claims** a bug would violate: the correctness invariant, the test *oracle*, the project invariants (`docs/ARCHITECTURE.md` §2), determinism / safety, API / version compatibility. The reviewers' job is to break these.

2. **Pick the lenses** — distinct, non-overlapping, matched to the change's real failure axes (mine them from `textbooks/reference/ANTI_PATTERNS.md` and the project's invariants). **Width rubric (#312)** — declare the class before spawning; the step-4 verdict record carries the forced line `effort: <class> → N lenses`: **moderate** (reversible, no invariant / trust-boundary / public-surface touch) → 1–2 · **standard** (the default feature / machinery slice) → 3 · **critical** (security, trust boundary, data-loss path, public API / schema, merge-gate machinery, D-NN-adjacent) → 4–5, hard cap. Grounding: `research/notes/agent-project-systems.md` — per-class effort-scaling rules are production-proven, a 3-diverse-reviewer panel measured 30%+ higher detection at trivial cost, and past the cap extra reviewers buy Ruflo-shaped overhead, not coverage. Neutral defaults to adapt:
   - **Lens A — core correctness / logic / math:** hand-verify the central logic by worked example; check spec↔impl and producer↔consumer parity; enumerate edge cases (empty / degenerate input, boundaries, overflow, off-by-one).
   - **Lens B — language / framework / resource soundness:** the stack's footguns (memory / ownership, concurrency / races, resource lifecycles, error handling, API misuse) + **refactor regressions** (did an extraction change observable behavior?).
   - **Lens C — test / oracle integrity + invariants:** do the tests actually *prove* the claim (could a wrong impl still pass?); **fixtures must discriminate** — for any rule with two readings (precedence, tie-break, aggregation, normalization, identity), ask *"what configuration would make the wrong reading fail?"* and demand a fixture where the readings diverge (ANTI_PATTERNS "The Agreeable Fixture" — exact assertions on agreeing fixtures prove nothing); **changed tests are guilty until proven** — diff the test files specifically: a loosened assertion, widened tolerance, new skip, or real-call→mock swap must trace its justification to the spec, not to making the new code pass; **a regression corpus is a claim about the class, not the instance** — where the diff closes a bypass, name the axis it varies along and demand the *boring* member plus a must-**not**-fire neighbour, since a corpus that grew by exactly one case is unfinished (ANTI_PATTERNS "The Half-Closed Class"; a mutation killing zero cases is a corpus gap, not a pass); **the guard's own prose is under review too** — every capability its docs advertise either names a fixture that exercises it or gets narrowed in the same change (ANTI_PATTERNS "The Guard That Advertises More Than It Enforces"); coverage gaps; conformance to the library (verify `Book NN §X` citations) and the project invariants; CI-vs-local reality.
     - **Hand this lens the author's mutation table, and require it to beat it (#845).** A mutation table is real evidence but its *coverage* is bounded by the author's own hypothesis space — it kills exactly what the author thought to try, while reading as far stronger proof than that. So the lens's job is not to admire it: **for each fix, propose a specific mutation you believe would SURVIVE the suite, and name the test that should have caught it.** Every survivor is then either a new test or a deleted inert guard. In the #823/#824/#825 commissions this single instruction produced the majority of the HIGH findings — and those were defects in the *fixes*, not the components being fixed.
   - *(add as needed)* **security / abuse**, **performance / resource**, **data / migration**.
   - *(add for feature-heavy or abstraction-heavy diffs)* **over-engineering / YAGNI:** falsify the claim *"this is the minimal sufficient implementation."* Flag, biggest cut first: **delete** (dead / unreachable / unused), **stdlib** or **native** (hand-rolled what the language or platform already ships), **yagni** (a single-implementation interface, a one-caller indirection layer, a speculative flag or config nobody sets), **shrink** (same behavior in materially fewer lines). The bar is *cut without loss* — never at the cost of the non-negotiables in `CLAUDE.md` › Working style (validation, error/data-loss handling, security, determinism, the explicit ask). Inert over-engineering is a Low/Med, not a Critical; rank by lines/deps removable. This lens is the **per-diff** half (cruft as it enters); for **accumulated** cruft a single diff can't show — a one-impl interface, a flag nobody sets — run [`audit_over_engineering`](../audit_over_engineering/SKILL.md) (whole-repo, on-demand).
   This composes `review_against_library` (the conformance lens) and `/code-review` (the generic-bug lens).

3. **Fan out the reviewers in parallel — read-only.** **The fan-out *is* the skill, not an upgrade to it — dispatch, don't ask (#817).** Invoking this skill **is** the standing request for these subagents, so a session posture of *"no subagents unless the user requested it"* is already satisfied: spawn them, and name them in the report. Never spend an approval round-trip on a daily gate, and never quietly substitute a solo self-read — one context grading its own diff is the confirm-bias this skill's opening line names, and it emits an *identical-looking* report, so `definition_of_done` step 10 passes a milestone exit over a review that never ran. A dispatch the harness **denies** routes to the denial protocol (`CLAUDE.md` › Working style); the report then says **solo, not multi-lens**, in those words. Delegate to `/code-review ultra` (cloud multi-agent), the **Workflow tool** (one read-only agent per lens in a Review phase), or parallel `Agent` subagents in a single message — **preferring the [`adversarial-reviewer`](../../agents/adversarial-reviewer.md) agent type**: its toolset is Read/Grep/Glob only, so "read-only" is enforced by the harness, not the prompt — and it carries no `model:` pin, so **every lens runs on the session model** (the #49 anti-goal: judgment never routes down). Execution belongs to step 4's verify stage, never to a lens or a bare general agent. Give each reviewer: the repo path, the exact diff / files, the claims to falsify, its lens, and the **output contract** — every finding tagged **SEVERITY (Critical / High / Med / Low)** with `file:line`, a concrete repro or worked argument, and a suggested fix; *attempt to falsify before concluding*; **state plainly what is solid** (don't invent issues to look productive); and **ask, never guess (#309)** — a detail the handout is missing (a file not provided, an unstated claim, an ambiguous lens boundary) comes back as a question in the report, never a plausible fill. **Evidence only from tools actually held (#493)**: a Read/Grep/Glob reviewer has no git, shell, or CI access, so it never asserts working-tree, CI, or any other process state — such a claim is fabrication even when plausible (a downstream hit it live: two reviewers "quoted" `git status` on a tree verified clean); state it can't observe, it reports as *unverifiable*. Reviewers **return findings; they do not modify files.**

4. **Reconcile + triage.** Dedupe across lenses; **void any finding whose evidence the reviewer's toolset could not have observed** (working-tree / CI / process state — #493), a voided finding that names a real risk is re-derived from static evidence or, if runtime, routed onward; **the verify stage — execute runtime claims, never adjudicate them (#827):** a finding asserting runtime behavior (fails-on-X / flaky / perf) routes to a [`repro-verifier`](../../agents/repro-verifier.md) dispatch (`isolation: "worktree"`; commit the diff first — worktrees see committed state) returning CONFIRMED / REFUTED / UNRUNNABLE, standing-granted like the lens fan-out (#827; dispatch, don't ask — inline verification is the #817 substitution); contributor diffs run only on explicit owner authorization (conventions); record an overall verdict (e.g. SOUND / SOLID-with-gaps), *why* (what was hand-verified), and the `effort: <class> → N lenses` line (step 2's rubric — the forced artifact that keeps width a declared decision, #312). Split into **FIX-NOW** (Critical / High / Med + cheap high-value Low) vs **DEFER** (genuinely non-blocking).

5. **Apply the must-fix set — coordinated, non-trampling.** Default: fix **serially** in the working tree. If you parallelize independent fixes, give each its **own worktree / branch** and merge back (disjoint files only); re-verify after the merge. Then re-run `definition_of_done` — the fixes must not regress the gates. Fold them into the same PR (pre-merge) or a clearly-labelled follow-up PR.

6. **Ticket every DEFER finding** — invoke `track_followups`. A finding left only in chat or a PR comment is lost next session; this is **not optional.**

7. **Harvest the lesson — a finding class seen twice becomes standing text (#306).** Tickets park *work*; lessons change the *standing text* later sessions actually read — a recurring class left ticket-only is re-found forever. Before closing: for each FIX-NOW/DEFER class, check for a prior sighting (`gh issue list --state all --search "<keywords>"` + the findings tables in earlier review PRs). **Second sighting ⇒ graduate it** up the prevention ladder (`retrospective` step 4 — most mechanical rung that holds): a gate/audit assertion; an `ANTI_PATTERNS.md` entry + `SYMPTOMS.md` signature (regen `SECTIONS.json`, run the audits) so pre-mortems see it; a standing lens line in this skill; or a skill Don't / conventions rule (a SKILL.md diff rides the evolution loop's eval gate — `EVALS.md`). **The prune rides the harvest**: whichever home you touch, sweep its existing entries in the same PR and remove the ones whose trigger can no longer recur (the guarded machinery changed or died) — "ten specific rules outperform 100 generic ones" (compounding engineering, `research/notes/agent-project-systems.md`). Repeat-finding rate across later reviews is the success metric — mined from review history at retro time, not new tooling.

## Output

- A findings table: severity · `file:line` · issue · verdict (fixed / ticketed-as #N / confirmed-solid).
- The synthesized verdict + what was hand-verified.
- The fix-now commit(s) + the ticket number(s) for deferred items.
- A `lessons:` line — `lessons: none (no second sightings)` or one `lessons: <home> — <entry>` per harvest (+ what the rode-along prune removed). The report is incomplete without it.

## Verification

- Reviewers genuinely attempted to falsify — reports carry worked counter-arguments, not check-marks.
- Where a mutation table was supplied, the test-oracle lens **proposed at least one mutation it expected to survive** — and each proposal was run, not just reasoned about. A lens that only validates the author's table has not done this job.
- **The review phase touched no files** — the diff after the fan-out equals the diff before it; every edit came from the coordinated fix pass.
- Every runtime claim carries its `repro-verifier` outcome — CONFIRMED / REFUTED with output; UNRUNNABLE or a denied dispatch is corrected and re-dispatched, or ticketed — never silently dropped (#827).
- Every Critical / High / Med is fixed **or** explicitly accepted with a ticket; nothing merges / closes with an unaddressed one.
- Every deferred finding has a ticket (`track_followups` ran); none lives only in the conversation.
- The report carries its `lessons:` line; any second-sighted class left a lesson in a durable home, and every home touched by a harvest was pruned in the same PR.

## Don't

- **Don't let reviewers edit the tree.** The parallel phase is read-only; a reviewer that writes can clobber another's context and corrupt the review. Findings only.
- **Don't apply parallel fixes to the same files.** Serialize, or isolate each fix in its own worktree / branch and merge back. Two writers on one tree is the trampling failure mode.
- **Don't downgrade the fan-out to a solo read, and don't ask permission for it (#817).** The report renders the same either way — that identical shape is what makes the substitution dangerous; a genuinely denied dispatch is disclosed as **solo, not multi-lens**.
- Don't run reviewers that "confirm" — the mandate is to break the claims from distinct angles.
- Don't let the lenses overlap; diverse angles are the whole point.
- Don't merge / close with an unresolved Critical / High, or with findings parked only in chat.
- Don't reach for the fan-out on trivial changes — that's `/code-review`'s job.
- Don't let the same finding class get re-found review after review — two sightings means a lesson in standing text (step 7), not another ticket; and don't harvest first sightings — one occurrence is an incident, not a pattern.
- Don't execute on the checkout while the fan-out shares it — building/testing/repro is `repro-verifier`'s job in its own worktree (#827); and don't verify a runtime claim inline — the #817 substitution, one stage later.
- Don't trust a device / environment-specific finding as cleared by CI when CI can't exercise it; note what only ran on the dev machine.
- Don't accept a reviewer's claim about state its tools can't observe — findings cite Read/Grep/Glob evidence, or they're void (#493).
